# Apertus 8B integration status

Target: [`swiss-ai/Apertus-8B-2509`](https://huggingface.co/swiss-ai/Apertus-8B-2509), base checkpoint at commit `3162c99675aa588097cecd4a24b9aa1f712af477`.
The [Apertus technical report](https://github.com/swiss-ai/apertus-tech-report), [published training-code repository](https://github.com/swiss-ai/pretrain-code), and [Transformers implementation](https://github.com/huggingface/transformers/blob/main/src/transformers/models/apertus/modeling_apertus.py) are architecture references. The training-code repository's current default branch contains Apertus 1.5 scripts; the pinned 2509 checkpoint and its Transformers implementation define this adapter's exact tensor layout and forward behavior.

## Implemented

- The Hugging Face package dispatches `model_type: "apertus"` for text generation. It validates the supported config, reads a single SafeTensors file or indexed shards, checks every expected tensor and shape, and exposes full-prefix forward plus fixed-capacity KV-cache prefill/decode Programs. Linear weights keep their checkpoint layout and transpose as graph views, so CUDA initialization copies BF16 tensors directly without large JavaScript arrays.
- The forward graph includes grouped-query attention, per-head Q/K RMSNorm, Llama 3 RoPE scaling, independent output head, and the two-matrix xIELU MLP. BF16 checkpoint tensors remain BF16 in parameter storage and matmuls. RMSNorm variance, attention softmax, and the xIELU `expm1` approximation use f32 intermediates where BF16 loses needed range or precision. The model runs on CPU and CUDA.
- The tokenizer loader handles Apertus's isolated Unicode-regex `Split` followed by ByteLevel pretokenization, applies the configured BOS token, and checks special token IDs.
- A deterministic two-layer fixture is generated by `packages/@affon/huggingface/test/generate-apertus-reference.py` with Transformers 4.57.6 and PyTorch 2.14.1. Native CPU logits and all hidden states match the independent f32 reference within `2e-4`. A BF16 variant verifies BF16 parameter initialization and logits within `0.02` of the Transformers BF16 reference.
- The actual 17 MB tokenizer was tested locally against Transformers on English, Chinese, emoji, accents, whitespace, numbers, and empty input. This asset is not checked into the repository.

## Scope and memory

The full-prefix path remains for correctness checks; generation can use fixed-capacity KV caching. There is no training loop. The [checkpoint index](https://huggingface.co/swiss-ai/Apertus-8B-2509/blob/main/model.safetensors.index.json) reports 8,053,338,176 BF16 parameters: **15.0 GiB** for weights alone. On the user's RTX 3090 (24,576 MiB total), the pinned four-shard checkpoint was downloaded and each weight shard checked against its published SHA-256. PyTorch 2.11.0+cu128 and Transformers 5.16.1 loaded the complete BF16 model in 2.52 seconds and ran a three-token forward pass in 0.237 seconds. Peak CUDA reserved memory was 16,131,293,184 bytes (15.02 GiB), with 8,595,111,936 bytes free afterward. This establishes that full-checkpoint inference fits that GPU with the short prompt in the reference implementation.

Affon validated and loaded all 451 checkpoint tensors and initialized the BF16 parameters into a CUDA Session. An initialization-only probe reported **15,860 MiB GPU memory used and 8,261 MiB free** in `nvidia-smi`. The CUDA recipe enumerator in the sibling Compute repository was extended to expose supported primitive kernels; both small Apertus fixtures then matched their independent logits references on CUDA (maximum errors `0.0000057` for f32 and `0.00146` for BF16).

With the full checkpoint, Affon and Hugging Face both predicted token **6174** for `[1, 7, 9]`. For the tokenizer-produced prompt `The capital of Switzerland is`, both predicted token **10518**, decoded as ` Bern`. All 131,072 logits were finite. After the CUDA stream fix below, the real-prompt maximum absolute logit difference was `1.25` and the mean absolute difference was `0.257`; the three-token probe had maximum `1.625` and mean `0.304`. These are functional inference checks, not a claim of bitwise full-logit parity. Affon's earlier real-prompt run took **1:29** end to end, including checkpoint load, CUDA initialization, graph compilation, and forward execution; peak host RSS was about **28.1 GiB**. CUDA peak VRAM during the forward has not been sampled continuously.

### Full-checkpoint BF16 parity diagnosis

The initial embedding and first attention RMSNorm output matched PyTorch exactly. Subsequent probes exposed a CUDA correctness bug: the same binary, checkpoint, and tokens sometimes produced different first-block key/value projections and even different next tokens. The loaded tensors had identical SHA-256 values across runs, and GPU copies of the key/value weights matched the checkpoint bytes. A standalone BF16 matmul using those inputs also varied on repeated executions. Compute created its kernel stream as non-blocking while its buffer transfers used synchronous copies on the default stream; changing the kernel stream to participate in default-stream ordering removed the variability. The standalone key/value matmuls were identical across three repeated processes, and two independent full-model runs produced byte-identical 131,072-logit arrays and token 6174. Earlier one-run parity numbers and the first-block causal substitution were affected by this race and should not be used to assess numerical precision.

At the time of the original parity probe, Affon's BF16 CUDA matmul used a serial f32 accumulator and rounded once to BF16. The current cuBLAS BF16 dispatch uses a different GPU algorithm; full-logit parity should be measured again on that path. The earlier numbers in this section describe the old kernel.

The two PyTorch attention implementations also differ: SDPA versus eager attention gives maximum final-logit difference `2.3125` and mean `0.2441` on the same checkpoint and tokens, with the same next token. This establishes a precision-sensitive baseline for the remaining Affon-to-PyTorch differences; it does not by itself identify their source.

### RTX 3090 token rate

With Strata stopped, a loaded Affon CUDA Session generated five additional tokens after the six-token prompt `The capital of Switzerland is`. The earlier full-prefix path achieved **0.50 tokens/s** including a compile for each new sequence length, or **0.72 tokens/s** for forward execution alone. Its five forwards took `1.063`, `1.197`, `1.351`, `1.499`, and `1.795` seconds as the prefix grew from 7 to 11 tokens. Compilation added `0.546`–`0.695` seconds per length.

Before the cuBLAS change, the fixed-capacity KV-cache path at capacity 512 generated the same continuation IDs (`1044`, `1799`, `1395`, `2095`, `1278`) at **3.27 tokens/s** for decode execution. Decode compiled **once** in `0.597` seconds, then the five token steps took `0.304`, `0.299`, `0.319`, `0.298`, and `0.307` seconds. The token position is a runtime input to that one Program and executable; it does not trigger a new compilation per token. Prefill compiled in `0.434` seconds and its cold execution took `3.082` seconds. The app's generation call, after model load and CUDA parameter initialization, took `5.91` seconds for six new tokens including prefill, compilation, and decode. These are short single-run wall-clock samples, not sustained throughput measurements.

The serving app now initializes the CUDA Session and compiles a 320-token decode Program before reporting ready, reusing it across requests. It also compiles the default prompt length's prefill Program. The first one-token request after ready took `3.15` seconds through the local SSH tunnel, versus about `46` seconds when CUDA parameter initialization happened on demand. Other prompt lengths still require a prefill compile.

For context, the same checkpoint in PyTorch 2.11.0+cu128 and Transformers 5.16.1 on the same RTX 3090 generated those IDs at **38.62 tokens/s** with KV caching. Its warm six-token prefill took about `0.025` seconds. Affon now reuses K/V states and its compiled decode graph, but remains substantially slower. The CUDA profile below identifies the largest measured cost.

### CUDA decode profile

Nsight Systems 2023.4.4 traced `test/benchmark/hf-inference/apertus-profile.ts` on the RTX 3090 using the same checkpoint, a six-token prompt, fixed KV capacity 320, and 16 generated tokens. The first step was prefill (`3.067` seconds); the following 15 cached steps took `0.319`–`0.336` seconds each. The kernel totals below exclude prefill, segmented at the first decode matmul in the CUDA trace. They are accumulated device kernel durations, so they do not include host scheduling or gaps between kernels.

| Decode kernel | 15-step GPU time | Approximate time/token |
| --- | ---: | ---: |
| `compute_matmul_small` | 3,308 ms | 221 ms |
| `compute_reduce1_f32` | 378 ms | 25 ms |
| `compute_index_small` | 116 ms | 8 ms |
| `compute_copy_small` | 79 ms | 5 ms |
| Other kernels | 126 ms | 8 ms |

Before the cuBLAS change, matmul accounted for about **83% of decode kernel time**. The old BF16 `compute_matmul_small` path assigned one output element to each thread and accumulated the inner dimension serially in f32; it did not use the RTX 3090's tensor cores. The LM head alone took about `16` ms per decode step. The fixed-capacity cache copy was measurable but was not the main source of the gap. These trace totals do not establish that matmul explained the entire Affon-to-PyTorch wall-time difference.

The general CUDA BF16 matmul dispatch now calls cuBLAS `cublasGemmEx` for supported contiguous and transposed layouts, retaining the scalar kernel for irregular layouts. At fixed capacity 320, the same 16-token Apertus output was generated; the 15 cached steps improved from **3.09 to 8.54 tokens/s** (single runs). Nsight's follow-up trace confirms Ampere BF16 tensor-core GEMM and cuBLAS BF16 GEMV kernels. `compute_reduce1_f32` is now the largest individual kernel family in the traced run. The remaining gap to PyTorch needs a fresh per-phase profile; the earlier 38.62 tokens/s PyTorch sample used a short five-token continuation.

### Rank-one mean reduction follow-up, 2026-10-31

[Compute commit `ace797f`](https://github.com/neucine/compute/commit/ace797f) routes rank-one f32 means of at least 32 elements through the existing cooperative CUDA reduction. The short path and min/max reductions retain their previous dispatch. On the RTX 3090, the same checkpoint, six-token prompt and 320-token cache produced identical 16-token continuations before and after the change. Two unprofiled runs per binary measured **8.25 and 8.02 tokens/s before**, and **9.26 and 9.48 tokens/s after**, counting only the 15 cached decode steps. These are small samples from a CUDA parity snapshot, not a current-main model baseline. The [run record](../../test/benchmark/results/apertus-cuda-rank1-mean-2026-10-31.json) retains every step time and binary hash.

Whole-run CUDA traces, including prefill, show the reduction family falling from **528.6 to 79.6 ms** across the same 28,245 launches. At width 4096, matched operator timing fell from **0.267 to 0.031 ms**. The new [four-width rank-one catalog](../../test/parity/catalogs/cuda-f32-apertus-mean-4.json) passed all numerical, operator and Program checks against PyTorch; the [pre-change batch](../../test/benchmark/results/parity-cuda-f32-apertus-mean-before-2026-10-31/report.md) missed numerical tolerance at width 8192, while the [optimized batch](../../test/benchmark/results/parity-cuda-f32-apertus-mean-optimized-2026-10-31/report.md) passed it. A separate rank-one check covered dense, offset and strided views.

[Compute commit `3e4f20d`](https://github.com/neucine/compute/commit/3e4f20d) makes the CUDA BF16 `index_select` path validate host-current rank-one indices before launch, avoiding a GPU error-flag allocation and stream synchronization for those calls. The [four-cell CUDA index parity batch](../../test/benchmark/results/parity-cuda-index-fastpath-2026-10-31/report.md) passed all numerical, operator and Program comparisons on the RTX 3090; an invalid BF16 index still failed synchronously, followed by a successful valid run of the same executable. The identical checkpoint and output IDs measured **9.83 and 10.25 cached tokens/s** in two runs, versus **9.26–9.48** after the preceding reduction change. The [run record](../../test/benchmark/results/apertus-cuda-index-host-validation-2026-10-31.json) retains step times. The two runs used different PTX compiler outputs; the committed build uses the focused CUDA 12.4 PTX guard from the 10.25 tokens/s run.

[Compute commit `d096ef1`](https://github.com/neucine/compute/commit/d096ef1) routes f32 `index_select` through the same four-byte indexing kernel, fixing a separate older CUDA path that accepted invalid indices. The [CUDA bounds worker](../../test/parity/workers/cuda-index-bounds.ts) rejected high and negative indices for f32 and BF16 and verified recovery on a valid call. Its [four-cell parity rerun](../../test/benchmark/results/parity-cuda-f32-index-bounds-2026-10-31/report.md) passed numerical, operator and Program comparisons. This correction was tested in the isolated CUDA parity snapshot; its source uses an older recipe interface than current Compute main. Apertus uses BF16 indexing, so no new model token-rate claim follows from the f32 correction.

[Compute commit `39a4c5d`](https://github.com/neucine/compute/commit/39a4c5d) flattens the RoPE `[1, 1, heads, half_width]` concatenation into one CUDA kernel instead of issuing a copy for each head and input. In a whole-run trace, `compute_copy_small` fell from 58,896 calls and about 110 ms in the preceding trace to 20,496 calls and 38.6 ms; 960 concat kernels added 1.26 ms. The [five-cell CUDA cat parity batch](../../test/benchmark/results/parity-cuda-rope-cat-2026-10-31/report.md) passed numerical, operator and Program checks. A [shape-specific worker](../../test/parity/workers/cuda-rope-cat.ts) matched PyTorch CUDA for f32 and BF16 with 8 and 32 heads in both operator and Program form; its [results](../../test/benchmark/results/cuda-rope-cat-pytorch-2026-10-31.json) are retained. Apertus output IDs stayed identical. In paired runs on the isolated snapshot, the baseline measured **9.81 cached tokens/s** and the changed build measured **9.68 and 10.04**. Excluding the first cached step, which incurs a one-time kernel setup cost, those rates were **9.89** before and **9.95–10.30** after. The [run record](../../test/benchmark/results/apertus-cuda-rope-cat-2026-10-31.json) keeps every step time; the short-run wall-time gain is modest and variable despite the clear reduction in copy launches.

The remaining full-model targets include BF16 GEMM (212 ms in the preceding trace) and the index kernel (114 ms in the latest trace, across 1,070 launches). Copy time is now about 39 ms in the latest trace. The index host validation removes synchronization but does not shorten its GPU kernel; the next indexing improvement needs a matched shape and a new model rerun. The older aggregate CUDA parity summary gives many unrelated cells nearly the same ratio because its timing boundary is dominated by fixed overhead.

### Matched CUDA operator and full Program comparison, 2026-10-31

The [Apertus-shaped matmul catalog](../../test/parity/catalogs/cuda-apertus-decode-matmul.json) passed numerical, operator and two-operation Program checks against PyTorch CUDA. The [other decode catalog](../../test/parity/catalogs/cuda-apertus-decode-ops.json) passed index selection and softmax. These timing scopes include synchronized output materialization; the Program peer is an operation followed by an add, not the complete Apertus decode graph.

| Case | Affon operator | PyTorch operator | Affon two-op Program | PyTorch two-op Program |
| --- | ---: | ---: | ---: | ---: |
| BF16 matmul 1 × 4096 × 4096 | 0.128 ms | 0.092 ms | 0.130 ms | 0.092 ms |
| BF16 matmul 1 × 4096 × 14336 | 0.386 ms | 0.271 ms | 0.392 ms | 0.275 ms |
| BF16 index select 320 × 128 | 0.0206 ms | 0.0128 ms | 0.0232 ms | 0.0158 ms |
| f32 softmax 32 × 320 | 0.193 ms | 0.0917 ms | 0.195 ms | 0.0973 ms |

The [full generation comparison](../../test/benchmark/results/apertus-program-peer-2026-10-31.json) used the same checkpoint, six-token prompt, 16 generated IDs and RTX 3090. Affon's fixed-capacity 320-token decode measured **10.17 and 10.66 cached tokens/s**; PyTorch's dynamic-cache SDPA decode measured **40.45 and 42.28**, and eager attention measured **40.61 and 41.02**. All generated IDs agreed. The full-prefix [131,072-logit comparison](../../test/benchmark/results/apertus-full-logit-parity-2026-10-31.json) found the same top token and top-ten set, mean absolute error **0.0935**, and 131,071 logits within **0.5** of PyTorch SDPA; one differed by **1.875**. On the first cached decode step, Affon versus [PyTorch eager](../../test/benchmark/results/apertus-cached-logit-parity-eager-2026-10-31.json) had mean absolute error **0.115** and maximum **0.75**; versus [PyTorch SDPA](../../test/benchmark/results/apertus-cached-logit-parity-sdpa-2026-10-31.json) it had mean **0.201** and maximum **3.25**. Both selected token 1044 and shared the top-ten set. [PyTorch eager versus SDPA](../../test/benchmark/results/apertus-cached-logit-peer-variance-2026-10-31.json) itself differed by mean **0.150** and maximum **2.5** on that step. These checks establish measured numerical proximity and identical greedy output, not exact bitwise equality.

The [paired CUDA trace summary](../../test/benchmark/results/apertus-program-trace-2026-10-31.json) isolates 15 cached steps in each run. Affon issued **6,769 kernels per step** and spent **43.96 ms** in their GPU execution; PyTorch issued **2,198** and spent **22.28 ms**. Median span from the first to last kernel was **95.24 vs 24.27 ms**, revealing substantial additional time between Affon kernels. The main BF16 GEMM family took about **212 ms** in both whole-run traces; Affon's additional indexing, reductions and copies account for much of the GPU difference. These traces include instrumentation overhead and use different cache representations, so their kernel spans are diagnostic rather than a deployment latency claim.

The decode-op catalog also exposed a **standalone BF16 RMSNorm failure** (`BackendFailure`) in the isolated CUDA snapshot, including its preexisting short-row cell. Apertus uses a primitive norm graph rather than that backend operation. The isolated snapshot contains CUDA cuBLAS edits outside committed Compute main; its binary hash and the trace hashes are retained in the results. The full Program scripts are [Affon profile](../../test/benchmark/hf-inference/apertus-profile.ts), [PyTorch profile](../../test/benchmark/hf-inference/apertus-pytorch-profile.py), and [comparison](../../test/benchmark/hf-inference/apertus-compare-program.py); the [cached logit worker](../../test/benchmark/hf-inference/apertus-cached-logits.ts) checks stateful numerical output.

Two [decode graph probes](../../test/benchmark/results/apertus-fusion-probes-2026-10-31.json) kept the 16 generated IDs but gave no speedup. Replacing the primitive f32 RMSNorm graph with the native operation raised the median of cached steps 7–14 from **88.30 to 100.15 ms** in paired single runs. Factoring the shared `beta × up` term out of xIELU measured **88.91 ms**. Both edits were reverted. The native normalization path needs its own kernel and scheduling profile before it can replace the primitive graph; a small algebraic reduction in graph nodes did not materially change full decode time.

### Grouped attention without KV head expansion, 2026-10-31

The [Apertus attention change](../../packages/@affon/models/src/apertus/model.ts) reshapes query heads into KV groups and uses batched matmul broadcasting for K and V. This removes the two `index_select` expansions per layer and avoids materializing full-head K/V arrays. The [retained GPU runs](../../test/benchmark/results/apertus-grouped-attention-2026-10-31.json) measured **14.17 and 14.24 cached tokens/s**, versus **10.17 and 10.66** in the preceding full-program comparison. Steady cached steps were about **67.16 ms**, versus **88.30 ms** in a recent paired baseline run. All 16 generated IDs agreed, and both the full-prefix and first cached BF16 logit rows were byte identical to the previous Affon output. Four Apertus fixture tests passed, including f32/BF16 numerical checks against PyTorch fixtures. These CUDA timings still come from the isolated parity snapshot with cuBLAS edits outside committed Compute main.

Full-parameter training on one 3090 is out of budget: BF16 weights and gradients need about 30 GiB combined; two f32 Adam moment buffers add 60 GiB, and an optional f32 master copy adds 30 GiB. Those figures exclude activations and CUDA allocations. A small continued-training run needs adapter training with quantized or CPU-offloaded frozen base weights, activation checkpointing, and a short context. A first experiment could use rank-8 LoRA, sequence length 512, microbatch 1, gradient accumulation 16, and a small licensed text sample, then record peak allocated/reserved VRAM and loss against a fixed baseline. This requires a native quantized/adapter training path or an external training harness; neither is part of this milestone.
